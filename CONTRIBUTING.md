## Getting Started

**Prerequisites:** Node.js 18 or later and npm.

```bash
# Fork and clone the repository
git clone <your-fork-url>
cd learn-dicoding

# Install dependencies
npm install

# Start the development server
npm run dev
```

The app is served at `http://localhost:5173`. The server performs hot module replacement on file save — no manual refresh needed.

## Project Architecture

The app follows a unidirectional data flow pattern with no framework dependency.

```
User interaction
      |
      v
  main.ts  (event delegation)
      |
      v
  store.ts  (dispatch -> reducer -> notify)
      |
      +---------> reducer.ts  (pure state transition)
      |
      +---------> storage.ts  (localStorage persistence)
      |
      v
  render.ts  (state -> DOM)
```

Key design rules that must be preserved:

- **`reducer.ts` is a pure function.** It has no side effects. Do not import `store`, `storage`, or any DOM API inside it.
- **`render.ts` is a pure render function.** It receives state and a root element. It does not import `store` or dispatch any actions.
- **`store.ts` is the single source of truth.** All state reads go through `getState()` and all writes go through `dispatch()`.
- **`main.ts` owns all event wiring.** Do not add event listeners in `render.ts`.

## Development Workflow

1. Create a branch from `main`:

```bash
git checkout -b <type>/<short-description>
# Examples:
#   feat/due-dates
#   fix/toggle-no-op
#   refactor/render-helpers
```

2. Make your changes and write or update tests.
3. Verify the build and test suite pass before opening a pull request.

```bash
# Type-check and build
npm run build

# Run all tests
npm test
```

## Code Conventions

### TypeScript

- Strict mode is enabled (`strict: true` in `tsconfig.json`). All code must compile without errors or warnings.
- No unused locals or parameters (`noUnusedLocals`, `noUnusedParameters`). Remove dead code rather than commenting it out.
- Use explicit types for function signatures. Avoid `any`.
- Define new types and interfaces in `types.ts`. Keep the rest of the modules free of ad-hoc inline type definitions for shared shapes.

### State and Actions

- All new state transitions belong in `reducer.ts` as a new `case` in the `switch` statement.
- New action shapes must be added to the `Action` union in `types.ts`. The exhaustive `default` case in the reducer will surface any unhandled action at compile time.
- State is always updated immutably — use spread syntax rather than mutating the existing state object.

### DOM and Rendering

- Build DOM nodes programmatically with `document.createElement`. Do not use `innerHTML` string templates.
- Assign `aria-label`, `role`, and `aria-live` attributes to interactive and dynamic elements. Follow the patterns in `render.ts`.
- Use `id` attributes and `data-*` attributes for event delegation targets, matching the patterns already in `main.ts`.

### File Naming

- Source files use `camelCase` (e.g., `taskHelpers.ts`).
- Test files use the pattern `<module>.<type>.test.ts` where type is `unit` or `property`.
- Use kebab-case for directory names.

## Testing

The project uses [Vitest](https://vitest.dev) as the test runner with [happy-dom](https://github.com/capricorn86/happy-dom) as the DOM environment. Property-based tests are written with [fast-check](https://fast-check.dev).

### Test Categories

| Category | File pattern | Purpose |
|---|---|---|
| Unit | `*.unit.test.ts` | Deterministic input/output scenarios, edge cases, and guard conditions |
| Property | `*.property<N>.test.ts` | Invariants that must hold for any input generated by fast-check |

### Running Tests

```bash
# Single pass (CI / pre-submit)
npm test

# Watch mode (during development)
npm run test:watch

# Interactive browser UI
npm run test:ui
```

### Writing Unit Tests

Follow the structure in `reducer.unit.test.ts`:

- Group tests by action type or function using `describe`.
- Use a `makeTask(overrides)` factory pattern to avoid repetitive fixture setup.
- Test the success path, the validation failure path, and guard conditions (e.g., unknown ID is a no-op) for every action that touches tasks.
- Assert exact state reference equality (`expect(next).toBe(state)`) on no-op paths to confirm no unnecessary allocations.

```typescript
import { describe, it, expect } from 'vitest';
import { reducer } from '../reducer';
import type { AppState, Task } from '../types';

function makeTask(overrides: Partial<Task> = {}): Task {
  return {
    id: 'task-1',
    title: 'Default title',
    completed: false,
    createdAt: '2024-01-01T00:00:00.000Z',
    ...overrides,
  };
}
```

### Writing Property-Based Tests

Follow the structure in `reducer.property1.test.ts`:

- Import shared arbitraries from `arbitraries.ts`. Add new arbitraries there rather than defining them inline.
- State the invariant clearly in a JSDoc comment above the test, including which requirements it validates.
- Use `fc.assert(fc.property(...))` with `{ numRuns: 100 }`.
- Return `false` from the property predicate (rather than throwing) to let fast-check shrink failing inputs.

```typescript
import * as fc from 'fast-check';
import { arbitraryTaskList, arbitraryTitle } from './arbitraries';

fc.assert(
  fc.property(arbitraryTaskList, arbitraryTitle, (tasks, title) => {
    // ... return true if invariant holds, false otherwise
  }),
  { numRuns: 100 }
);
```

### Test Coverage Expectations

Every new feature or bug fix must include:

- At least one unit test covering the happy path.
- At least one unit test covering validation failure or guard conditions where applicable.
- A property-based test for any logic that must hold across arbitrary inputs (e.g., new reducer cases, storage serialisation).

## Commit Messages

Use the following format:

```
<type>(<scope>): <short summary>

[optional body — explain the why, not the what]
```

**Types:**

| Type | When to use |
|---|---|
| `feat` | A new feature visible to the user |
| `fix` | A bug fix |
| `refactor` | Code change that is not a feature or a fix |
| `test` | Adding or updating tests only |
| `docs` | Documentation changes only |
| `chore` | Build, config, or dependency updates |

**Scope** is the module name: `reducer`, `render`, `storage`, `store`, `validation`, or `types`.

Examples:

```
feat(reducer): add CLEAR_COMPLETED action to remove all completed tasks
fix(storage): handle QuotaExceededError when saving tasks
test(render): add property test for filter bar active state
docs: update CONTRIBUTING with property test guidelines
```

Keep the summary line at or under 72 characters. Use the body to explain motivation or trade-offs when the change is non-obvious.

## Submitting Changes

1. Confirm the build passes with no TypeScript errors:

```bash
npm run build
```

2. Confirm all tests pass:

```bash
npm test
```

3. Push your branch and open a pull request against `main`.
4. Fill in the pull request description with:
   - What the change does and why.
   - Which area of the codebase is affected (`reducer`, `render`, etc.).
   - Any trade-offs or open questions.
5. Address review feedback with new commits. Do not rewrite history on a branch that is already open for review.
